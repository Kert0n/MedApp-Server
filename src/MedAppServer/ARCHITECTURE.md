# Архитектура MedApp Server

## Обзор

Сервер отвечает за синхронизацию общих аптечек, учёт препаратов и выдачу каталога лекарств.
Kotlin, Spring Boot, JPA/Hibernate, PostgreSQL.

Аптечка общая: у неё нет владельца, участники равноправны. Отсюда почти всё остальное —
блокировки на изменении остатка, инвариант «сумма планов не больше остатка», каскадные
удаления.

## Слои

| Пакет | Что там |
|---|---|
| `controller/` | HTTP: разбор запроса, маппинг ответа, коды состояния. Ничего больше |
| `api/` | DTO запросов и ответов + мапперы (`Mappers.kt`) |
| `services/orchestrators/` | Операции на стыке нескольких агрегатов |
| `services/models/` | Операции одного агрегата плюс командные типы (`Commands.kt`) |
| `services/security/` | JWT, хеширование, ограничение частоты запросов |
| `db/repository/` | Запросы и проекции слоя хранилища |
| `db/model/`, `db/model/parsed/` | Сущности JPA и доменные операции на них |
| `config/` | Объявление бинов: кеши, OpenAPI, свойства и проверки старта |

### Разрешённые связи

Направление одно: `Repo → Service → Orchestrator → Controller`.

| Пакет | Может импортировать |
|---|---|
| `db.model` | только `db.model` |
| `db.repository` | `db.model` |
| `services.security` | `db.model` |
| `services.models` | `db.model`, `db.repository`, `services.security`, `services.models` |
| `services.orchestrators` | `db.model`, `services.models`, `services.security` |
| `api` | `db.model`, `db.repository`, `services.models` |
| `controller` | `api`, `config`, `services.*` |
| `config` | всё, кроме `controller` — это composition root |

**Таблица закреплена `ArchitectureTest`** (Konsist, идёт в обычном `./gradlew test`).
Нарушение роняет сборку. Правила заведены не для красоты: за время разработки все они были
нарушены, и ни одна утечка не была видна ни компилятору, ни тестам поведения.

Три ребра оставлены сознательно и внесены в таблицу как исключения:

- `services.models → services.security` — `hashPassword`, `generateKey`, `hashToken` —
  криптографические утилиты, а не чужая бизнес-логика.
- `api → services.models` — мапперам команд (`toCommand`, `toPatch`). Представление вправе
  знать прикладной слой; обратное запрещено отдельным правилом.
- `config → services.orchestrators` — composition root объявляет бины кешей, в сигнатурах
  которых стоит `IntakeOutcome`.

## Оркестраторы — вынужденный редфлаг

Оркестратор заводится **только** когда операция стоит на стыке нескольких агрегатов или
задаёт транзакционную границу. Pass-through-методы запрещены: если оркестратор просто
пересылает вызов в сервис, он не нужен.

Сейчас их три, и каждый обязан объяснять своё существование:

- **`MedKitDrugServices`** — операции, затрагивающие аптечку и её препараты сразу: перенос
  между аптечками, удаление аптечки с миграцией, чтение содержимого одной транзакцией.
- **`IntakeService`** — приём с защитой от повторного применения. Нетранзакционный: списание
  обязано быть закоммичено до попадания результата в кеш идемпотентности, иначе откат оставил
  бы в кеше результат операции, которой не было. Вызов транзакционного метода того же класса
  пошёл бы мимо прокси Spring, поэтому это отдельный бин.
- **`TreatmentPlanService`** — заведение и правка плана. Читает остаток препарата под
  пессимистичной блокировкой, то есть трогает чужой агрегат.

`QuantityReductionService` был четвёртым и удалён: все три его входа оказались операциями
одного агрегата `Drug` и переехали в `DrugService` вместе с математикой сжатия планов,
уехавшей на саму сущность.

Существование `TreatmentPlanService` целиком держится на пессимистичной блокировке. Если
проект перейдёт на `@Version` с принудительным инкрементом при правке плана, обе его операции
вернутся в `UsingService`: всё прочее, что им нужно, достаётся по графу.

## Агрегаты

**`Drug` — корень агрегата, владеющий планами.** `Drug.usings` объявлена с `CascadeType.ALL`
и `orphanRemoval`: удаление препарата уносит планы, исключение плана из коллекции удаляет
строку. Отсюда требование, которое легко нарушить: путь, правящий коллекцию, обязан загрузить
её графом — по неинициализированной коллекции каскад проходит впустую.

**`Using` — связь, а не подчинённая запись.** У неё составной ключ `(userId, drugId)`, обе
связи `EAGER`, и `UsingService` ведёт её через свой репозиторий. Это законно ровно до тех
пор, пока он не начинает ходить в чужие репозитории: тем и отличается работа со связью от
координации агрегатов.

Инварианты живут на сущностях, а не в сервисах: `Drug.availableQuantity`,
`Drug.consumePlanned`, `Drug.shrinkPlansToStock`, `Using.reduceBy`.

## Граница DTO

api-типы живут в `api` и `controller`. Сервисы принимают скаляры или командные типы
(`DrugCreation`, `DrugPatch`, `PlanSnapshot`, `NewCredentials` в
`services/models/Commands.kt`), репозитории возвращают свои проекции (`MedKitSummary`).
Маппинг — только в `api/Mappers.kt`.

Валидация входа (`@Size`, `@DecimalMin`) остаётся на DTO: это свойство контракта.

## Модель данных

| Сущность | Назначение | Ключевые поля |
|---|---|---|
| `User` | Пользователь без персональных данных | `id`, `hashedKey` |
| `MedKit` | Общая аптечка | `id`, связи с пользователями и препаратами |
| `Drug` | Препарат в аптечке | `name`, `quantity` (`numeric(19,6)`), `totalPlannedAmount` (`@Formula`), `quantityUnit`, `medKit`, `usings` |
| `Using` | План лечения | `usingKey(userId, drugId)`, `plannedAmount` |
| `VidalDrug` | Каталог препаратов | `name`, `nameLat`, `activeSubstance`, `manufacturer`, `searchTsv` |

Количества — `BigDecimal` со scale 6, нормализация в сеттерах сущностей.
`Drug.totalPlannedAmount` считает `@Formula` при загрузке, поэтому сравнивать его можно
только по значению, никогда через `equals`.

## Кеши

Четыре бина в `config/CacheConfiguration.kt`, все на Caffeine через aedile:

- `medKitTokenCache` — share-ключи аптечек в хешированном виде, с TTL;
- `successfulRegistrationsCache` — счётчик регистраций по адресу;
- `loginAttemptsCache` — счётчик попыток выдачи токена;
- `intakeResultsCache` — результаты приёма для идемпотентности (`IntakeOutcome`).

## Безопасность и приватность

- Персональных данных нет: только технические идентификаторы. Адреса клиентов попадают
  в кеши только хешированными.
- JWT с ограниченным сроком действия, ключи подписи не в репозитории.
- Прод не поднимается с пустым или заглушечным секретом регистрации
  (`config/RegistrationSecret.kt`).
- Тела ошибок намеренно грубые: `ApiExceptionHandler` возвращает класс проблемы, но никогда
  не называет запись или количество.
- Логи пишутся только в stdout.

## Проверки

```bash
./gradlew test          # поведение + ArchitectureTest
./gradlew queryPlanTest # формы планов горячих запросов, отдельно (нужен Docker)
```

`StatementCountTest` следит за числом операторов, `queryPlanTest` — за тем, что запросы
попадают в индексы. Обычные тесты этот класс дефектов не видят: все три найденных N+1
проходили на зелёном наборе.
