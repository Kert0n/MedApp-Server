# Изменения схемы, применяемые вручную

Flyway в проекте сознательно не используется: инструмент добавляет трение в разработке,
а проект небольшой и схему можно менять с остановкой сервера.

Но одну вещь надо держать в голове: **`ddl-auto=update` никогда не удаляет и не меняет
существующие колонки — только добавляет.** Поэтому изменения, которые Hibernate сам не
сделает, живут здесь.

## Что Hibernate сделает сам

- добавление новой таблицы;
- добавление новой nullable-колонки;
- добавление индекса, объявленного в `@Table(indexes = ...)`.

Для этого достаточно `ddl-auto=update` в dev и обновлённого `../schema.sql`.

## Что придётся написать сюда

- удаление колонки или таблицы;
- смена типа колонки (например `double precision` → `numeric(19,6)`);
- сужение длины (`varchar(N)` при меньшем N, `text` → `varchar`);
- добавление NOT NULL к существующей колонке;
- переименование чего угодно.

## Порядок

1. Скрипт называется `NNN_короткое_описание.sql`, нумерация строго возрастает.
2. Скрипт идемпотентен, где это возможно (`IF EXISTS`, `IF NOT EXISTS`).
3. В том же коммите обновляется `../schema.sql` — иначе на чистой БД получится схема,
   отличная от продовой.
4. В таблицу ниже добавляется строка: применён ли скрипт на проде.

## Применение на проде

```bash
docker compose stop med-app-server
docker compose exec -T postgres psql -U "$POSTGRES_USER" -d medapp-server-db < db/manual/NNN_....sql
docker compose start med-app-server
```

Сервер останавливается потому, что в проде стоит `ddl-auto=validate`: он упадёт при
старте, если схема не совпадает с сущностями, и это здесь полезно — несовпадение видно
сразу, а не в первом же запросе.

## Чего этот подход не даёт

Проверки, что скрипт применён везде. Расхождение dev и prod остаётся на дисциплине —
это принятая цена отказа от Flyway. Таблица ниже и есть весь учёт.
