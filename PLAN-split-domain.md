# План: довести раздельную модель до конца

Подзадача эксперимента `spike/split-domain-drug`. Основной план проекта — `~/.claude/plans/wondrous-munching-dusk.md`, там же этот раздел продублирован.

## Контекст

Спайк доказал, что разделение работает на одном агрегате: 241 тест зелёный, SQL совпал полностью. Осталось проверить главное — как раскладка ведёт себя, когда её доводят до конца: все агрегаты, все правила по местам, ни одной сущности наружу. Заодно закрывается объём PR-06 и PR-07: MedKit становится корнем, межагрегатные коллекции исчезают, оркестратор остаётся только там, где use case трогает больше одного агрегата.

Конвенция имён уже задана правками в дереве: **отображение — `<Имя>Data`, чистое имя принадлежит домену**.

Два решения, принятые к этому шагу:
- **Доменный тип получает каждая сущность**, включая пользователя и справочник. Для пользователя это ещё и место, куда наконец переезжает Spring Security: `UserData` перестаёт быть `UserDetails`.
- **Членство — явная сущность** `MedKitMembershipData` на той же таблице `user_med_kits`. Схема не меняется: те же имена ключей и каскадов, иначе `CascadeSchemaTest` и сравнение с `db/schema.sql` перестанут сходиться.

## Ключевое следствие: формы чтения упраздняются

Раз домен есть у всего, отдельные `DrugView`, `TreatmentPlanView`, `DrugTemplateView` теряют смысл — репозиторий может отдавать сразу доменный тип. Отсюда:

- `db/repository/Projections.kt` исчезает; `api/Mappers.kt` собирает DTO из доменных типов.
- **`@Formula storedPlannedTotal` уходит вместе с ними.** Она существовала ради того, чтобы список препаратов приходил с суммами одним запросом. Теперь читающий запрос забирает препараты вместе с планами (`join fetch`), а сумму считает домен — определение остаётся одно, и оно в домене.
- Счётчики аптечки (`MedKitSummary`) строить агрегатом нельзя: считать участников и препараты, поднимая их в память, — это ровно тот сценарий, ради которого проекция и заводилась. Она остаётся, но переезжает в домен как значение `MedKitOverview`, то есть тип «форма чтения» исчезает, а запрос-счётчик — нет.

**Это место надо измерить, а не объявить.** Чтение списка препаратов было одним запросом с подзапросом-формулой; станет одним запросом с `join fetch` планов — столько же обращений, но больше строк. Если по логу выйдет иначе, факт идёт в `SPIKE.md` как минус варианту.

## Хранилища вместо репозиториев наружу

Сервисы перестают видеть сущности вовсе. На каждый агрегат заводится хранилище (`db/store/DrugStore.kt`, `MedKitStore.kt`, `UserStore.kt`, `CatalogueStore.kt`), которое оборачивает Spring Data-репозиторий и говорит только доменными типами:

```
load / lock  → доменное состояние
save(state)  → берёт управляемую сущность по идентификатору и применяет состояние
delete(id)
```

`save` не делает лишнего запроса: внутри той же транзакции сущность уже в persistence context, и `findById` берёт её оттуда. Резолверы `User`/`MedKit`, которые в первом заходе торчали в сервисе, уезжают внутрь хранилища — там для них есть репозитории.

## Что где живёт

**Домен** — правила: остаток и планы (`domain/drug`, готово); членство, вступление, выход последнего участника (`domain/medkit`); идентичность пользователя (`domain/user`); карточка справочника как значение (`domain/catalogue`).

**Сервисы** — транзакция, проверка доступа и её 404, выдача и разбор ключа приглашения (кеш + `SecurityService`), сборка DTO. `DrugService`, `MedKitService`, `UserService`, `CatalogueService` (бывший `VidalDrugService`).

**Оркестраторы** — только то, что трогает больше одного агрегата: создание препарата в аптечке, перенос препарата, выход из аптечки (членство + планы участника во всех её препаратах через bulk `deleteByUserIdAndMedKitId`, который наконец получает вызывающего), удаление аптечки с переносом. `MedKitDrugServices` переименовывается в `MedKitDrugOrchestrator`.

## Порядок работ

1. **Достроить конвенцию имён:** классы `MedKit` → `MedKitData`, `TreatmentPlan` → `TreatmentPlanData` (файлы уже переименованы). Вернуть тесту домена имя `DrugAggregateTest` — он проверяет домен, а не отображение.
2. **`domain/medkit/MedKit.kt`** — неизменяемый агрегат: `id`, `members: Set<UUID>`; `join`, `leave` (с признаком «стала пустой»), `isMember`/`requireMember`. Инварианты: аптечка не бывает без участников, повторное вступление отвергается, доступ есть только у участника.
3. **`MedKitMembershipData`** + удаление `MedKitData.userData`, `MedKitData.drugData`, `UserData.medKits`. Запросы `MedKitRepository` и `EXISTS`-подзапросы в `DrugRepository` переводятся на явные джойны по членству. Здесь же чинятся `@EntityGraph(attributePaths = ["drugs"|"users"])`, которые после переименования указывают на несуществующие свойства.
4. **`domain/user/User.kt`** + `UserStore`; `UserData` перестаёт реализовывать `UserDetails` — адаптер переезжает в `services/security`.
5. **`domain/catalogue`** — карточка справочника доменным значением, `CatalogueStore` отдаёт её напрямую; `Projections.kt` удаляется.
6. **Хранилища** для всех четырёх агрегатов, сервисы переводятся на них, `db.model.*` из сервисов исчезает.
7. **Оркестратор** собирается заново под четыре межагрегатных сценария.
8. **Тесты:** `MedKitAggregateTest` без Spring; правки там, где тесты держались за сущности и `View` (`DatabaseTestHelper`, `ReadProjectionTest`, `RepositoryIntegrationTests`, контрактный тест).

## Как проверяем

- `./gradlew test` — все 241 зелёные, проверки поведения не ослабляются. Ослабленный тест — результат эксперимента, а не деталь реализации.
- **SQL по логу до и после** на трёх сценариях: чтение списка препаратов аптечки, снимок пользователя, команда над препаратом. Число запросов не должно вырасти; рост числа строк из-за `join fetch` фиксируется числом.
- `open-api.yaml` не меняется — публичный контракт эксперимент не трогает.
- Схема не меняется: `db/schema.sql` тот же, `CascadeSchemaTest` и `SchemaContractTest` зелёные.
